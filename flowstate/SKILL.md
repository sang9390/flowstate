# flowstate — 지시 파이프라인 + 상태관리

모든 지시는 아래 7단계를 순서대로 통과한다. 명확한 지시는 P2~P3에서 채울 빈칸이 없으므로 즉시 통과되어 오버헤드가 거의 없다. 각 단계를 지날 때 한 줄 상태를 출력한다. 형식: `[flowstate P3/7 해소] images = ./images (facts에서 확인)`

## P1. Intake (정규화)

- 지시 원문을 그대로 보존한다 (해석하기 전에).
- 프로젝트 루트에 `.flowstate/facts.md`가 없으면 `references/fact-protocol.md`의 초기 골격으로 생성한다.
- lemmalog 엔진이 미연동이면(`lemmalog_*` MCP 도구 부재) `scripts/setup-lemmalog.sh`를 실행한다. 멱등 스크립트 — 세팅돼 있으면 즉시 통과하고, 최초 1회만 rustup(~1.5GB)+빌드(수 분)가 걸린다. 등록은 다음 세션부터 적용되므로 현재 작업은 파일 모드로 계속한다. 단, 환경변수 `FLOWSTATE_NO_SETUP=1`이 설정돼 있으면 세팅을 건너뛴다(격리 실행·벤치마크용).
- 기존 facts.md가 있으면 ACTIVE 섹션을 읽어 현재 상태를 파악한다.

## P2. Spec화

지시를 5항목 task spec으로 변환한다:

- **목표**: 무엇이 달성되어야 하는가
- **대상**: 어떤 파일/엔티티/범위인가
- **제약**: 하지 말아야 할 것, 지켜야 할 조건
- **완료 조건**: 무엇이 확인되면 끝인가
- **진단**: Localization(기본값 — 대상만 최소 변경, 무관한 코드·구조 불변) 또는 Generalization(구조적 결함이거나 반복될 문제라는 근거가 있을 때만). Generalization을 고르면 근거를 한 줄로 명시한다. 임의 범위 확장·과잉 설계 금지.

확정할 수 없는 항목은 `?빈칸`으로 표시한다. 추측으로 채우지 않는다.

## P3. 해소 (빈칸 채우기)

`?빈칸`을 아래 순서로 채운다. 순서를 건너뛰지 않는다:

1. **fact store 조회**: facts.md ACTIVE 섹션에서 관련 사실 검색. "아까 그 함수" 같은 축약 지시는 최근 `@asserted` 사실부터 역순으로 매칭.
2. **구조 분석**: 파일시스템(Glob), 코드(Grep/Read)를 직접 조사해 후보를 좁힌다. 후보가 하나로 수렴하면 채택하고 근거를 상태 줄에 출력.
3. **사용자 질문**: 위 두 단계로도 후보가 2개 이상이거나 0개면, 그때만 질문한다. 질문 시 조사로 찾은 후보를 함께 제시한다.

**반환각 규칙**: 미지의 변수, 모호한 요구, 예상외 오류를 만나면 추측으로 메우지 않는다. 대화형이면 중단하고 질문한다. 질문이 불가능한 비대화형 실행이면 가장 보수적인(가역적이고 범위가 좁은) 기본값을 택하고, 그 결정과 근거를 facts.md에 `@src=derived:...`로 기록한 뒤 최종 답변에도 명시한다.

lemmalog MCP 도구(`lemmalog_query`, `lemmalog_why` 등)가 사용 가능하면 1번 조회를 엔진에 위임한다. 없으면 파일 검색으로 수행한다.

## P4. 계획

- 복잡도에 비례해 분해한다: 실행 단계가 3개 이상이면 계층 구조(트리)로 분해하고 단계 간 의존성을 명시한다. 1~2단계 과제는 한 줄 계획으로 충분 — 형식을 위한 분해는 하지 않는다.
- 3단계 이상으로 분해한 과제는 **최종 답변에도** 그 분해와 단계 간 의존성(무엇이 무엇에 선행했는지)을 표기한다. 계획 단계에서만 쓰고 답변에서 생략하지 않는다.
- 계획 범위는 P2 진단을 따른다. Localization이면 계획에 무관한 파일·구조 변경을 넣지 않는다.

**적응형 게이트 (P4 → P5 경계)**: 아래 중 하나라도 해당하면 실행 전에 멈추고 확인받는다. 해당 없으면 무정지 진행한다.

- 파괴적/비가역 작업 (삭제, 덮어쓰기, 외부 전송, 이력 변경)
- spec의 대상·제약을 벗어나는 범위 확장
- Generalization 진단으로 구조를 바꾸는 경우

비대화형 실행에서 게이트에 걸리면: 해당 작업만 제외하고 나머지를 진행하며, 제외 사실과 이유를 최종 답변에 명시한다.

## P5. 실행

- 계획된 단계를 수행한다.
- 실행 중 새로 알게 된 사실(파일 위치, 함수 역할, 버그 원인, 사용자 결정)은 **그 자리에서** facts.md ACTIVE에 기록한다. 형식과 confidence 기준은 `references/fact-protocol.md`를 따른다.

## P6. 기록 (풍화)

- 이번 작업에서 내린 결정, 발견한 패턴, 반증된 가정을 facts.md에 반영한다.
- 역할 분리: **facts.md**에는 개별 사실(라인 프로토콜), 프로젝트에 `docs/knowledge_graph.md`가 있으면 구조·관계·설계 결정은 그쪽에 노드/엣지로 갱신한다. 같은 내용을 두 곳에 중복 기록하지 않는다.
- **반증된 사실은 절대 삭제하지 않는다.** RETIRED 섹션으로 이동하고 `@to`(마감 시각)와 `@reason`을 붙인다.
- 철회된 사실이 유일한 근거(`@src`)였던 파생 사실도 함께 철회한다(연쇄 철회).
- lemmalog MCP가 있으면 신규 사실을 `lemmalog_observe`로 동기화한다. 엔진 스냅샷은 프로젝트별 `.flowstate/lemmalog.snapshot`에 자동 저장됨(MCP 등록 시 상대 경로 지정) — 프로젝트 간 상태 섞임 없음. facts.md와 불일치 시 facts.md가 진실의 원천.

## P7. Handoff

사용자가 마무리, 세션 전환, 인수인계를 요청하면 `references/handoff-template.md` 양식으로 문서를 생성한다. facts.md의 ACTIVE 스냅샷이 진실의 원천이다.

## 작업 종료 시 상태 요약

매 작업 끝에 3줄 이내로 보고한다:

- 기록/철회된 사실 수 (예: `facts: +3 기록, 1 철회`)
- 남은 `?빈칸` 또는 미해결 항목
- 권장 다음 단계 (없으면 생략)
